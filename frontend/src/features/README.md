# `features/` — where domain logic lives

Three folders can hold code for the same domain. This is the split, so it does not drift:

| Folder | Holds | Example |
| --- | --- | --- |
| `pages/` | The route entry. Layout and composition only — no fetching, no form state. | `ProjectsPage.jsx` |
| `features/<domain>/` | That domain's TanStack Query hooks, mutations, and forms. | `features/projects/useProjects.js`, `ProjectForm.jsx` |
| `components/<domain>/` | Presentational pieces that take props and render. | `components/project/ProjectCard.jsx` |

Rule of thumb: if it calls the API or holds form state, it belongs in `features/`.
If it only takes props and renders, it belongs in `components/`.

Shared, domain-agnostic pieces (`DataTable`, `EmptyState`, `StatusChip`) go in
`components/common/`. Anything generated by the shadcn CLI stays in `components/ui/`
and is not hand-edited.

## Folders

- `auth/` — login, register, session bootstrap (Sprint 2)
- `projects/` — project queries, project form, member management (Sprint 3)
- `tasks/` — task queries, board state, progress mutations (Sprint 4)
- `reports/` — daily site report queries and form (Sprint 5)
- `issues/` — issue queries, status transitions (Sprint 5)
- `expenses/` — expense queries, budget summary (Sprint 6)

Server state belongs to TanStack Query. Zustand holds auth and UI state only —
copying server data into Zustand is the #1 source of stale-UI bugs (`PLAN.md` §6).
